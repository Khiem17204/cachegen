Cache reuse only matters if every benchmark prompt is deterministic, long enough to stress the prefill path, and easy to rebuild across machines without hidden downloads or private datasets. This text bundle exists for that purpose. It is intentionally repo-owned, plain text, and semantically repetitive enough that we can concatenate and slice it into exact tokenizer-length prompt windows for multiple benchmark runs.

The benchmark asks one narrow question: when we transfer a populated KV cache over a simulated network link, how much faster is the first generated token if we use CacheGen instead of a quantized FP8 KV-cache transfer baseline? That means the prompt source must not be the variable we are accidentally measuring. The prompt builder repeats this corpus, tokenizes it with the target model tokenizer, and then cuts exact token windows from deterministic offsets so every run stays reproducible.

Trustworthy TTFT measurements depend on a few mundane details that are easy to overlook. We want real vLLM execution, a warmed engine, stable prompt lengths, a fixed maximum decode budget, and explicit connector accounting for the exact serialized bytes that move through the simulated transport. We also want to fail loudly when CacheGen silently falls back to raw layer transfer, because that would make the headline comparison ambiguous.

Single-GPU Colab runs are not the full serving environment from the paper, but they are still useful when the scope is stated honestly. A single A100 can answer a practical question for this repository: does the CacheGen-style connector provide a clear TTFT benefit against an FP8 KV-cache transfer comparator under the same runtime, model, and bandwidth setting? Reporting the measured speedup clearly matters more than forcing the result into the paper range.

Serialization overhead belongs in the accounting. If the connector writes metadata, tensor wrappers, scales, and payload framing in addition to the raw compressed chunk bytes, the transmitted byte count should reflect that exact blob rather than a partial estimate. Once the transport accounting is honest, we can separate raw tensor bytes from transmitted bytes, compute a transport ratio, and break time into simulated network delay plus decode time.

Prompt windows built from deterministic offsets serve two goals at once. They let us reuse a single checked-in text bundle across models, and they avoid benchmarking the same exact prefix twice at every length. The first sample for a given length starts at offset zero. The second sample begins exactly one prompt window later in token space. That keeps the suite simple, inspectable, and easy to reproduce inside Colab or a local shell.

When the benchmark finishes, the report should contain enough metadata for another person to interpret the result without guessing. That includes the GPU name, CUDA version, torch version, vLLM version, the vLLM submodule commit, the benchmark repository commit, the benchmark configuration, every measured run, the per-mode summaries, and an explicit claim-check classification that says whether the observed 3 Gbps speedup falls below, within, or above the paper range.
